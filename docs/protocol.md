# 通信の取り決め（バージョン1）

iPhoneアプリ（クライアント）とWindowsサーバーの間の通信を定める。変更するときは、この文書とサーバー・アプリの両方を同時に直す。

## つなぎ方

- WebSocket（`ws://<ホスト>:8765/`）を1本だけ使う
- テキストフレーム: JSONの制御メッセージ
- バイナリフレーム: 映像（サーバー→クライアントのみ）
- サーバーは同時に1台のクライアントだけを受け付ける。新しくつながると、前の接続は切られる
- 外出先からは、WindowsとiPhoneの両方にTailscaleを入れ、Tailscaleのアドレスでつなぐ。ポートはインターネットに公開しない

## 認証

最初のメッセージは必ず `hello` にする。5秒以内に届かない場合、またはトークンが違う場合は、サーバーが `error` を返して接続を切る。

トークンは、サーバー初回起動時に作られ、`server/config.json` に保存される。リポジトリには入れない。

## バイナリフレームの種類

どのバイナリフレームも、先頭は、フラグ（1バイト）とタイムスタンプ（4バイト）。フラグの bit1 が立っていれば音、立っていなければ映像。

## 映像（バイナリフレーム）

`codec` が `hevc` のときは、H.264 の代わりに H.265（HEVC、Annex B 形式）。各フレームの先頭に AUD（NALタイプ35）、キーフレーム（IDR）の先頭に VPS、SPS、PPS（32、33、34）が付く。そのほかは、下の H.264 と同じ。

1つのバイナリフレームが、H.264の1フレーム（アクセスユニット）に当たる。

```
offset 0   : 1バイト  フラグ（bit0 = キーフレーム、bit1 = 0（映像））
offset 1-4 : 4バイト  タイムスタンプ（ミリ秒、ビッグエンディアン、接続開始からの経過）
offset 5-  : H.264（Annex B形式）
```

- 各フレームの先頭にAUD（NALタイプ9）が付く
- キーフレームには、SPSとPPSが先頭に付く。クライアントは、これを使ってデコーダーを作る
- Bフレームは使わない。キーフレームは約2秒おきに入る
- 映像の大きさは、`welcome` の `w`, `h` と同じ。途中で変わる場合は `resize` を先に送る

## UDP での映像と音

映像と音のバイナリフレームだけを、UDP でも送れる。制御（JSON）と、ファイルの受け渡しは、WebSocket のまま。入力（マウス、キー）も、WebSocket のまま。

### 選び方

- `hello` の `transport`: `tcp`（WebSocket だけ。初めの値）、`udp`（UDP で送る。つながらなければ、エラー）、`auto`（UDP を試して、つながらなければ、`tcp` にする）
- サーバーが UDP を使えるとき、`welcome` に `udp_port`（UDP のポート。WebSocket と同じ番号）と `udp_key`（16進の文字列、16文字。この接続だけの合言葉）を付ける。使えないときは、付けない（`udp` を頼まれた場合は、`error` を返して切る。`auto` なら、`tcp` で続ける）
- `udp_key` を付けた直後は、映像と音を、まだ WebSocket で送る。UDP がつながったら、クライアントが、`transport`（`mode`: `udp`。下の「UDP のつなぎ方」の 3）を送って、切り替える

### UDP のつなぎ方（クライアントから始める）

どのデータグラムも、先頭の1バイトが種類。

| 種類 | 向き | 中身 |
|---|---|---|
| `0x01` BIND | クライアント→サーバー | 8バイト: `udp_key`（16進を、バイトにしたもの） |
| `0x02` ACK | サーバー→クライアント | 8バイト: `udp_key`（同じもの） |
| `0x03` KEEPALIVE | クライアント→サーバー | なし |
| `0x10` 映像 | サーバー→クライアント | 下の「映像・音のデータグラム」 |
| `0x11` 音 | サーバー→クライアント | 同上 |

1. クライアントは、`udp_port` に、BIND を送る。返事（ACK）が来るまで、0.2秒おきに送り直す。3秒たっても ACK が来なければ、UDP をあきらめる（`udp` ならエラー、`auto` なら `tcp` で続ける）
2. サーバーは、`udp_key` が合う BIND を受け取ったら、その送り元（アドレスとポート）を、この接続の UDP の相手として覚え、ACK を返す。合わない BIND は、無視する。BIND は、何度届いても、同じ ACK を返す（送り元が変わっても、合っていれば、覚え直す）
3. ACK が届いたら、クライアントは、WebSocket で `transport`（`mode`: `udp`）を送る。サーバーは、これを受け取ってから（BIND が合っていなければ、`error` を返して、WebSocket のまま）、映像と音を、UDP で送り始める（WebSocket には、送らない）。切り替えの前後で、フレームが重なっても、欠けても、よい。クライアントは、次のキーフレームから、映す
4. クライアントは、UDP の使用中、2秒おきに KEEPALIVE を送る（ルーターの穴を保つため）。サーバーは、6秒、KEEPALIVE も BIND も受け取らなければ、WebSocket で `transport`（`mode`: `tcp`）を送って、WebSocket に戻す。戻した映像は、次のキーフレームから始める
5. クライアントは、いつでも、`transport`（`mode`: `tcp`）を送って、WebSocket に戻せる

### 映像・音のデータグラム

```
offset 0    : 1バイト  種類（0x10 = 映像、0x11 = 音）
offset 1-4  : 4バイト  フレーム番号（ビッグエンディアン。映像と音は、別々に、0 から数える。1つ増えるごとに、次のフレーム）
offset 5-8  : 4バイト  タイムスタンプ（ミリ秒。WebSocket のフレームと同じ時計）
offset 9    : 1バイト  フラグ（bit0 = キーフレーム。音は 0）
offset 10-11: 2バイト  分けた番号（0 から）
offset 12-13: 2バイト  分けた数（1 以上）
offset 14-  : 中身（映像は、WebSocket のフレームの、5バイト目から後ろと同じ。音は、Opus の1パケット）
```

- 1つのデータグラムの大きさは、1200バイト以下（中身は、1186バイト以下）。映像のフレームが大きいときは、分けて送る。音は、分けない（分けた数は 1）
- クライアントは、同じフレーム番号のデータグラムを集めて、分けた数が全部そろったら、1つのフレームにする。順番が入れ替わっても、同じ番号なら、そろえられる
- 新しいフレームが、先にそろったら、古い、そろっていないフレームは、捨てる。そろわないまま 100ミリ秒たったフレームも、捨てる
- 映像のフレームが欠けたら、クライアントは、次のキーフレームが来るまで、映像のフレームを、デコーダーに渡さない（直前の映像を出したままにする）。サーバーに、キーフレームは頼まない
- 音は、Opus のときだけ UDP で送る。PCM は、1つが大きく、分けられないので、UDP のときも WebSocket で送る（クライアントは、どちらで来ても受け取る）
- 欠けた音は、捨てる（再送しない）
- UDP のときは、キーフレームの間隔を、短くする（約0.5秒。`fps` の半分のフレーム数ごと）。欠けたあと、少しの間で、映像が戻るようにするため。TCP のときは、これまでどおり（約2秒）。サーバーは、`hello` の `transport` が `udp` か `auto` の接続では、撮り始めから間隔を短くし、接続の途中では変えない（`tcp` に戻しても、短いまま）
- 暗号化はしない。`udp_key` は、つなぐ相手が、合っているかの目印で、通信の秘密を守るものではない

## ゲームパッド

画面のスティックや、iPhone につないだ本物のコントローラの状態を、PC の仮想のゲームパッド（Xbox 360 のコントローラ）に、反映する。PC 側に、ViGEmBus（仮想のゲームパッドのドライバー）が要る。入っていなければ、使えない（`welcome` の `pad` が偽）。

- クライアントは、`welcome` の `pad` が真のときだけ、`pad` を送る（偽のときは、キーボードの入力で代用する。アプリの「キーボード入力」）
- サーバーは、`pad` を初めて受け取ったとき、仮想のゲームパッドを作り、`pad_state` を返す。以後の `pad` は、今の状態として、そのまま反映する（差分ではなく、毎回、全部の状態）
- クライアントは、状態が変わったときだけ送る。スティックを離したときは、必ず、0 の状態を送る（押したままにならないように）。送る頻度は、1秒に120回まで。まとめて送ってよい
- サーバーは、次のときに、仮想のゲームパッドの状態を、全部 0 にして、取り外す: `pad_off` を受け取ったとき、切断したとき、別の端末に替わったとき
- ゲームが振動を出したら、サーバーが `rumble` を送る。クライアントは、つないだコントローラがあれば、そのコントローラを振動させる（なければ、iPhone を軽く振動させてよい）
- スティックの値は、サーバーで、-32768〜32767 に、トリガーは、0〜255 に、直す。範囲の外の値は、範囲の中に収める。数でない値、型が違う値は、0 にする

ボタン（`b`）のビット（XInput の `XINPUT_GAMEPAD_*` と同じ値）:

| ビット | ボタン |
|---|---|
| `0x0001` | 十字 上 |
| `0x0002` | 十字 下 |
| `0x0004` | 十字 左 |
| `0x0008` | 十字 右 |
| `0x0010` | Start |
| `0x0020` | Back |
| `0x0040` | 左スティックを押す |
| `0x0080` | 右スティックを押す |
| `0x0100` | 左のバンパー（LB） |
| `0x0200` | 右のバンパー（RB） |
| `0x0400` | Guide（Xbox ボタン） |
| `0x1000` | A |
| `0x2000` | B |
| `0x4000` | X |
| `0x8000` | Y |

## ファイルの受け渡し（バイナリフレーム）

ファイルの中身は、どちらの向きも、次の形のバイナリフレームで送る。1つのフレームは 256KB まで。

```
offset 0   : 1バイト  フラグ（bit2 = 1。ファイル）
offset 1-4 : 4バイト  id（ビッグエンディアン。`file_put` か `file_begin` の id）
offset 5-  : 中身の続き
```

- iPhone→PC: 保存先は、PCの `ダウンロード\DuoRemote`。同じ名前があれば、名前に番号を付ける。`size` と送られた量が合わなければ、保存せずに `error`
- PC→iPhone: アプリは、受け取ったファイルを、共有の画面（保存、写真に追加など）で見せる。画像は、iPhone のクリップボードにも入れる
- 途中で切断したら、受け取りかけのファイルは捨てる

## 画質を自動で変える

アプリは、`stats` の `dropped` と、`ping` の往復の時間を見て、`quality` で画質を変える。決まりはアプリが持つ（サーバーは、言われたとおりにするだけ）。

## 複数のモニター

- `mode` の `monitor` で、そのモニター全体を映す。操作の座標は、そのモニターが基準
- `desktop`（仮想ディスプレイ）は、これまでどおり。仮想ディスプレイも `monitors` に出る（`virtual` が true）
- 主モニターは `screen` と同じ。返事は、どのモニターでも `mode`（`mode`: `monitor`、`id`、`name`）
- `monitors` の `id` は、Windows のモニターのデバイス名（例: `\\.\DISPLAY1`）。つなぎ直しても同じ。`name` は、画面に出す名前（例: `DISPLAY1`）
- `id` のモニターがなければ `error`。映せなかったときは、`error` と `mode`（`screen`）を送り、本物の画面に戻す
- `quality` は、設定が今と変わらないときは、撮り直さない

## スリープとロックを防ぐ

接続している間、サーバーは、PCがスリープしたり、画面が消えたりしないようにする（`SetThreadExecutionState`）。これで、何もしないでいるうちに画面がロックされることも防ぐ。切断すると、元に戻す。ロック画面と UAC の画面は、Windows の決まりで、今も操作できない。

## キーの送り方

- `vk`：Windowsの仮想キーコード（1〜254）。iPhoneのキーボードの横に出す Esc、Tab、矢印などに使う
- `sc`：キーの位置を表すスキャンコード。Bluetoothキーボードのキーは、全てこれで送る。どの文字になるかは、PCのキー配列（JIS、USなど）で決まる。拡張キー（矢印、Insert、Delete、右Ctrlなど）は、`0xE0` を上に付けて `0xE04B` の形にする。1バイトの値（1〜255）か、`0xE001`〜`0xE0FF` だけを受け付ける
- 両方あるときは `sc` を使う
- PCは、押したままのキーを自分では繰り返さない。押し続けたときの繰り返しは、クライアントが `down` を何度も送って行う
- 日本語キーボードの「英数」「かな」キーは、`key` ではなく `ime` で送る（「英数」でオフ、「かな」でオン）

## 音（バイナリフレーム）

- `codec` が `opus` のとき、音のフレームの中身は、Opus の1パケット（20ミリ秒、48000Hz）。帯域は、ステレオで約 0.1Mbps。そのほかの決まりは、下の PCM と同じ

- クライアントが `audio`（`on`: true）を送ると、サーバーはPCが鳴らしている音を取り、まず `audio_state`（`on`: true、`rate`、`channels`）を送ってから、音のフレームを送る。クライアントは、`audio_state` を受け取ってから、再生の準備をする
- 音のフレームは、フラグの bit1 が立つ。タイムスタンプは映像と同じ時計（接続開始からのミリ秒）。残りは、PCM（符号つき16ビット、リトルエンディアン、チャンネルはインターリーブ）で、約20ミリ秒ぶん
- 圧縮はしない。帯域の目安は、48000Hz・2チャンネルで約1.5Mbps、24000Hz・1チャンネルで約0.4Mbps
- PCが無音のときは、フレームは来ない（そのまま待つ）
- 通信が追いつかないときは、サーバーが古い音を捨てる
- 取れなかったとき、対応していない `rate` や `channels` のときは、`audio_state`（`on`: false、`reason`）を返す。映像と操作は、そのまま続く
- 音を止めるか、切断すると、サーバーは音の取得を止める

## ウィンドウ単位の表示

- `mode` で `window` を選ぶと、サーバーはそのウィンドウを前に出し、そのウィンドウを撮る。サーバーの ffmpeg に `gfxcapture`（Windows Graphics Capture。ffmpeg 8.1 以降）があれば、ウィンドウだけを撮るので、他のウィンドウが上に重なっても映らない。なければ、画面のウィンドウの範囲を切り抜くので、上に重なったものも映る
- `fit_w`, `fit_h` があれば、先にウィンドウの大きさを変える。iPhoneの画面のポイント数を送ると、1ポイントがWindowsの1論理画素（拡大率をかけた画素）になる大きさにする。作業領域に入らないときは、縦横比を保って縮める
- 返事の順番は、`mode`、`resize`（大きさが変わるときだけ）、新しい映像。新しい映像は、SPSとPPSの付いたキーフレームから始まる
- ウィンドウが動いたり大きさが変わったりすると、サーバーは撮り直し、`resize` を送る（同じ位置が0.5秒続いてから）。最小化している間は、前の範囲のまま
- ウィンドウが閉じられると、`error` と `mode`（`screen`）を送り、画面全体に戻す
- 画面を切り抜くときは、主モニターからはみ出した部分は撮らない。ウィンドウだけを撮るときは、はみ出した部分も撮る。どちらでも、どのモニターにも出ていないウィンドウは選べない（`error` を返す）
- ウィンドウだけを撮るときは、ウィンドウを動かしただけ（大きさが同じ）なら、撮り直さない（`resize` も送らない）
- ウィンドウだけを撮るとき、ffmpeg 8.1 では、ウィンドウの中身が変わったときにしか映像が来ない（中身が止まっていれば、フレームも来ない）。サーバーは、撮り始めに、最初の1枚が届くまでウィンドウに描き直しを頼む。キーフレームは、枚数ではなく時間で入れる（前のキーフレームから2秒たった次の1枚）
- 切断すると、範囲は画面全体に戻る

## 仮想ディスプレイ

iPhone専用の作業用の画面として、仮想ディスプレイ（Virtual Display Driver）を使う。ドライバーは、使わないときは無効にしておき、サーバーが、必要なときだけ有効にする（サーバーを管理者として起動しておく）。`welcome` の `virtual` が false のときは、使えない。

- `mode` の `desktop`: 仮想ディスプレイを有効にして、そのモニター全体を映す。`fit_w`、`fit_h`（iPhoneの画面のポイント数）があれば、その縦横比に近い解像度に変える（高さは 1080 にそろえ、幅だけを縦横比に合わせる）。サーバーは、出すのに時間がかかるとき、先に `notice` を送る。返事は `mode`（`desktop`）と、大きさが変わるときの `resize`
- `mode` の `window` に `to_virtual`: true を付けると、そのウィンドウを仮想ディスプレイに移し（作業領域いっぱいに広げる）、そこで映す。`fit_w`、`fit_h` は、仮想ディスプレイの解像度を決めるのに使う。`to_virtual` がなければ、ウィンドウが出ているモニターで、そのまま映す
- `bring`: ウィンドウを、仮想ディスプレイに持ってくる。`desktop` を映しているときに使う
- 持ってきたウィンドウは、元の位置（最大化の状態も）を覚えておき、次のときに戻す
  - `restore` を受け取ったとき
  - iPhoneが、正常に接続を閉じたとき（接続を閉じるときの番号が 1000。アプリの「切断」ボタン）。このときは、仮想ディスプレイも、すぐ無効に戻す
  - 通信が切れた、アプリが裏に回った、など、正常でない切れ方のとき。120秒待ってから戻す。この間に、同じ端末がつなぎ直せば、戻さずに、続きから使える
  - サーバーを止めたとき
- 別の端末がつないで、前の接続が切られたときは、戻さない（新しい端末が引き継ぐ）
- 仮想ディスプレイが、ドライバーの設定にある解像度から選ぶため、縦横比は、近いものになる（ぴったりとは限らない）
- 仮想ディスプレイを出す、解像度を変える間は、動いている撮影が無効になる（Windows の DXGI_ERROR_ACCESS_LOST）ので、サーバーは、先に撮影を止め、終わってから撮り直す。この間、映像は止まる（数秒）

## 撮影が止まったとき

- 撮影が途中で止まったとき（画面の設定が変わった、UAC の画面に切り替わった、ロック画面になった、など）は、サーバーが、接続を切らずに、撮り直す。待ち時間は、止まった回数に比例して延びる（1秒、2秒、…）。30秒のうちに5回を超えて止まったら、あきらめる
- あきらめたとき、本物の画面以外（仮想画面、ウィンドウ）を映していれば、`error`（理由つき）と `mode`（`screen`）を送って、本物の画面に戻す。本物の画面も撮れなければ、接続を閉じる（閉じる番号 1008、理由つき）

## 切断したとき

- サーバーは、押したまま離されていないマウスのボタンとキーを、すべて離す
- 仮想ディスプレイとウィンドウは、上の「仮想ディスプレイ」のとおりに戻す
